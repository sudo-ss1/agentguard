# Phase 3 design: identity and tokens

Approved 2026-09-27. Targets attack 4 (sub-agent reuses the parent's token) and attack 5 (forged
request claiming to be research-bot).

## Decisions

| Question | Decision |
| --- | --- |
| Agent identity | `did:key` (Ed25519, multicodec `ed25519-pub`, base58btc) generated by each agent with PyNaCl. |
| Credential | The identity service issues a W3C VC (Data Model 2.0) secured as JOSE with EdDSA. It binds the DID to sponsor, purpose, allowed tools and model version. |
| Request signing | DPoP (RFC 9449): a JWS per request over `htm`, `htu`, `iat`, `jti` and `ath`. One extra claim, `mcp: {method, tool, args_digest}` (RFC 8785 canonical JSON), binds the tool call itself. |
| Capability tokens | Biscuit. The root token is minted by the identity service. Sub-agents are delegated through a third-party block signed with the parent's DID key. |
| Attack 5 model | A forged request arriving at the gateway (no second agent). |
| Attack 4/5 drivers | New scripted payloads, and a step field `as: {agent, token}`. Scenarios 1–3 and 6 are unchanged. |
| Denial reasons (receipt exposure) | **Option C.** Reasons are structured: rule id, attribute names, and coarse values in the clear (e.g. `recipient_domain`, `url_host`, a path class). Precise values are salted commitments whose salts are stored off the ledger. |

## Verification at the gateway (offline)

The gateway checks each request in this order:

1. The VC signature, against the pinned issuer DID, and its expiry.
2. The DPoP signature, with the key of the VC subject's DID.
3. `iat` is within ±60 s, and `jti` has not been seen before.
4. `ath` matches the presented Biscuit, and the `mcp` claim matches the actual call.
5. The Biscuit is authorized with only the root public key. The authorizer supplies the facts
   `tool`, `holder` (the DID proven in step 2) and `time`, plus the rule
   `allow if tool($t), right($t)`. Every block's checks must also pass.

The principal for the allowlist and Cedar is the verified VC's agent name. `X-Agent-Id` is ignored.

## Token shape

The root token's authority block, signed by the identity service root key:

```
right("read_file"); right("fetch_url"); ...          // the VC's allowed tools
owner("did:key:zParent");
check if time($t), $t <= <now + 1h>;
check if holder($h), owner($h) or holder($h), delegate($h) trusting ed25519/<parent pubkey>;
```

A delegation to a sub-agent is a third-party block signed with the parent's DID key:

```
delegate("did:key:zSub");
check if tool($t), ["fetch_url"].contains($t);
check if time($t), $t <= <now + 5m>;
```

This is safe for three reasons:

- Blocks can only add checks.
- `right` and `delegate` facts are trusted only from the authority block or from blocks signed
  by the parent's key.
- Trailing blocks can't be stripped without breaking the signature chain.

## Key material in the lab

- Agent private keys are stored at `<lab>/keys/<agent>.key` with mode 0600. The identity
  service's keys live in their own folder.
- The gateway gets only public material: the issuer DID and the Biscuit root public key.
- In Docker these are separate volumes.
- Keys never appear in logs or receipts.

## Tests

- **Attacks 4 and 5:** baseline, the attack succeeds (strict xfail). Guarded, it must be blocked.
  The email target is `sam@lab.test`, which Cedar permits, so only the identity or token layer
  can stop it.
- **Offline authorization:** every token is authorized with the identity service stopped and
  outgoing network connections blocked.
- **Attack 4 token cases:**
  - narrowed token used for `send_email`
  - the parent's un-narrowed token reused by the sub-agent (the attack itself)
  - an unsigned widening block added by the sub-agent
  - the narrowing block stripped
  - an expired delegation
  - positive control: the narrowed token used for `fetch_url` is allowed
- **Identity:**
  - the did:key specification's test vector
  - a tampered VC
  - DPoP with the wrong key, a replayed `jti`, a stale `iat`, or an `mcp` claim that doesn't
    match the call
  - a positive control
- **Regression:** attacks 1–3 stay blocked with real identities.

## Implementation notes (identity, DPoP, tokens, gateway verification)

- **Pipeline order:** identity → capability token → pins → allowlist → declared arguments →
  Cedar. The token check runs before the gateway's local allowlist so each attack's receipt
  names the layer that answers it (attack 4: `capability-token`, attack 5: `identity`). If
  the allowlist ran first, the sub-agent in attack 4 would be stopped there instead, since it
  isn't listed, and the test would not prove the token caveat works.
- **Verification is middleware:** `IdentityMiddleware` reads each POST body once and verifies
  the VC, the DPoP proof and the token's signature chain. It never rejects a request itself:
  handlers deny unverified callers and write a receipt, so forgery attempts are logged.
- **The toolbox sends unlisted tools to a single server:** a caller isn't limited to the
  tools it is shown. When the toolbox is connected only to the gateway, a call to a tool the
  gateway didn't list still goes out, so the gateway records the attempt. Without this,
  attacks 4 and 5 were "blocked" by the client itself, with no gateway receipt. The attack
  tests now assert the expected gateway denial, and a mutation check confirmed they fail
  if that regresses.
- **The lab stops the identity service before starting the gateway:** every guarded run shows
  the gateway needs only the pinned issuer DID and Biscuit root public key.
- **Offline token tests:** tokens come from a real identity-service process, which is then
  stopped. Authorization runs with socket connections blocked, and a test checks the block is
  active. The block-stripping test removes the delegation block from the token's protobuf and
  re-encodes it. The result parses (`UnverifiedBiscuit`, one block fewer) but fails
  `verify(root)` with "failed verifying the signature". A control shows the re-encoding is
  byte-identical when nothing is removed.
- **Standards deviations:** the `mcp` claim in DPoP proofs. The proof carries `jwk` as
  RFC 9449 requires, and `kid` names the did:key. The verifier requires the `jwk` to equal the
  credential's key.
- **biscuit-python 0.4.0's type stubs lag its runtime** (`Algorithm.Ed25519`,
  `from_bytes(data, alg)`). Targeted `type: ignore`s explain this.

## Implementation notes (receipt option C)

- Reasons are structured: `rule`, `summary` (with no values) and `attributes`. Coarse
  attributes are kept in the clear from an explicit allowlist, and all other values are
  committed. Details, and where salts live, are in `docs/architecture.md`, under "Receipt
  exposure".
- Commitments use the SD-JWT disclosure digest (RFC 9901) over RFC 8785 JSON, with a random
  128-bit salt per value, stored in a separate 0600 salt store. In Docker the salt store is
  its own volume, mounted only into the gateway.
- `agentguard receipts prove` and `agentguard receipts forget` are the audit helpers.
  Forgetting a salt leaves the receipt log byte-identical.
- Verified on real attack 1 and attack 2 runs: no full recipient or exact path appears in the
  receipt log (`tests/test_receipts.py`).
